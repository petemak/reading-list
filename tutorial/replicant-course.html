      Part 1: How Replicant works
      

      Ten short ideas. Read them once, then build. You will meet every one of them again in Part 2.
      


      

      The one idea
      

      Your whole user interface is a function of your state. You write one ordinary Clojure function. It takes a map describing everything the app knows and returns a description of the entire page as data. Whenever the state changes, you call the function again and hand the new description to Replicant.
      

      Replicant remembers the previous description, compares it to the new one, and makes only the DOM changes needed to get from one to the other. That comparing step is called reconciliation, and it is the whole job of the library.
      

      The consequence for you: your view code has no state, no subscriptions and no side effects. It is a pure function you can call in a REPL and inspect like any other data. That is the part that makes Replicant pleasant.
      

      


      

      Hiccup in ten minutes
      

      The "description of the page" is hiccup: HTML written as Clojure vectors. A vector's first item is a keyword naming the tag. An optional map of attributes can come next. Everything after that is children.
      

      

      HiccupHTML it becomes
      


      [:p "Hi"]<p>Hi</p>
      

      [:a {:href "/about"} "About"]<a href="/about">About</a>
      

      [:div.card#main "x"]<div class="card" id="main">x</div>
      

      [:div {:class ["a" "b"]}]<div class="a b"></div>
      

      [:p {:style {:color "red"}} "!"]<p style="color: red">!</p>
      

      [:ul (for [x xs] [:li x])]one <li> per item
      

      [:div nil "shown"]nil children are skipped
      

      

      Because it is just vectors and maps, you build hiccup with the tools you already know: for, map, when, if, let, and small functions that return vectors.
      

      One rule that trips people up. Don't make the attribute map itself conditional, as in [:div (when x {:class "a"}) "text"]. Always pass a map and make the values conditional instead: [:div {:class (when x "a")} "text"]. Replicant warns about this in development.
      

      


      

      Hiccup in depth: vectors, maps and CSS
      

      Hiccup has one shape, and everything else is a variation on it:
      


      A vector is one HTML element. Its first item is always a keyword naming the tag. If the second item is a map, it holds the element's attributes. Everything after that is the element's content.
      


      The tag keyword
      

      The keyword is the tag name. You can also attach classes and an id with CSS-selector shorthand:
      


      The shorthand deliberately looks like the CSS selector that would target that element. .books in your stylesheet matches [:ul.books] in hiccup.
      


      The attribute map
      

      Each key becomes an attribute name and each value becomes its value:
      


      A few values get special treatment:
      

      

      Key or valueWhat happens
      


      true / false{:checked true} sets the attribute, while false or nil leaves it off. That's why :checked (:read? book) works directly in step 9.
      

      nil valuesAny attribute whose value is nil is simply omitted. That makes {:class (when (:read? book) "read")} clean: unread books get no class at all.
      

      :classThis can be a string, or a collection that Replicant joins with spaces. Collections are handy for combining conditional classes: {:class ["book" (when read? "read")]}. The nil gets dropped. Classes from the tag shorthand and from :class are merged.
      

      :styleThis takes a map, not a CSS string (see below).
      

      :onEvent handlers, as covered in Events as data.
      

      :replicant/...Instructions to Replicant, like :replicant/key and :replicant/on-mount. They never appear in the HTML.
      

      


      Children
      

      Anything after the tag (and the attribute map, if there is one) is content:
      


      Seqs being spliced in is what makes (map book-item books) and for work. They return a seq of vectors, and each vector becomes a sibling <li>. Nesting vectors inside vectors mirrors nesting tags inside tags, so the indentation of your hiccup reads like the indentation of the HTML.
      


      Inline styles: the :style map
      

      HTML's style="..." string becomes a Clojure map. Its keys are the CSS property names as keywords, in the same kebab-case CSS uses:
      


      I'd write values as strings with explicit units, like "8px". That way you never have to guess how a bare number will be interpreted.
      

      Because it's a map, style can be computed like any other data:
      



      Where CSS styling actually lives
      

      Hiccup describes elements, not stylesheets. There is no hiccup form for a CSS rule like .books li.read span { ... }. Styling is split into two jobs:
      

        

      • Your CSS file (or <style> block) defines what things look like, using selectors, just as in plain HTML. In the tutorial, that's the style block in index.html from step 4.
        • 

      • Your hiccup decides which elements match those selectors, by giving them tags, classes and ids based on state.
        • 

      

      Here's how the two line up in your reading list:
      



      When you tick the checkbox, the state changes and render-app runs again. This time the <li> gets class="read", so the CSS rule starts matching. Your Clojure code never touches a style; it only changes which class is present.
      

      Prefer classes for anything a stylesheet can express, and keep :style for values that are truly computed at runtime, like the progress-bar width above.

      What render actually does
      

      The main API is one function: (replicant.dom/render element hiccup).
      

        

      • The first time you call it on an element, Replicant builds DOM nodes from your hiccup and puts them inside that element.
        • 

      • Every later call on the same element compares the new hiccup with the last hiccup it rendered there, then adds, changes or removes only the nodes that differ. Unchanged nodes are left exactly as they were, which is why focus and cursor position survive a re-render.
        • 

      

      So Replicant never asks you "what changed?". You always give it the whole page; it works out the difference. That is what the blue flashes in the demo at the top show.
      

      


      

      Events as data
      

      Event handlers live in an :on map, named after browser events. A plain function works:
      


      But a function is not data. You can't print it, compare it or test it, and a fresh fn is created every render. Replicant's better option: put data in the handler slot, and register one global dispatch function that receives that data whenever the event fires.
      


      Replicant gives the data no meaning of its own. The convention of "a vector of action vectors" used in this course comes from the Replicant docs, and you are free to design your own.
      

      


      

      Keys for lists
      

      When you render a list and then remove the second item, how does Replicant know which <li> disappeared instead of assuming every item after it changed? You tell it, with :replicant/key:
      


      Use a stable, unique id from your data, never the position in the list.
      

      


      

      Life-cycle hooks
      

      Sometimes you need the real DOM node: to focus an input, measure something, or hand the node to a JavaScript charting library. Attach a hook as an attribute:
      

        

      • :replicant/on-mount runs when the node is first created.
        • 

      • :replicant/on-update runs when it changes.
        • 

      • :replicant/on-unmount runs when it is removed.
        • 

      • :replicant/on-render runs for all of the above.
        • 

      

      The hook receives a map containing :replicant/node, the actual DOM element. Hooks can be data too, in which case they go through your dispatch function. There are also :replicant/mounting and :replicant/unmounting, attribute overrides applied while a node enters or leaves, which make CSS fade-in and fade-out transitions declarative.
      

      


      

      Aliases
      

      Replicant deliberately has no components. What it has instead are aliases: your own tag names, written as namespaced keywords, that expand into ordinary hiccup.
      


      An alias is stateless. It receives attributes and children and returns hiccup. Replicant only re-runs it when its arguments change, and during development it uses the alias to produce more helpful error messages.
      

      


      

      Rendering to strings
      

      replicant.string/render turns the same hiccup into an HTML string, on the JVM or in the browser. Put your view functions in .cljc files and you can render them on the server for the first page load or for static sites, then take over in the browser.
      

      


      

      What it leaves out, on purpose
      

      Replicant is a rendering library and nothing else. It has no state management, no router, no HTTP helpers and no component-local state. You bring an atom and a few functions. That sounds like more work, and for the first hour it is. After that it means every part of your app is plain Clojure you already understand.

      Build for production
      
  
      Run the suite once from a clean start, then build an optimised bundle you can put on any static host.
      

  
      Stop the watcher first. While watch app is running, it rewrites public/js/main.js with a development build on every change, which would replace your release bundle.
      
  
      Preview the release build with Babashka
      
  
      The whole public/ folder is now your deployable site. To look at it locally, you'll serve it with Babashka, a Clojure scripting runtime that ships as a single native binary and starts in milliseconds. A small bb.edn file in the project gives you three short commands: bb test, bb release and bb serve.
      

  
      1. Install Babashka
      
  
      The official installer script downloads the right binary for your machine. By default it installs into /usr/local/bin, which needs sudo:
      

  
      If you'd rather not use sudo, install into your home directory instead with ./install --dir ~/.local/bin. On Ubuntu that folder is on your PATH once it exists, though you may need to open a new terminal (or log out and in) before bb is found.
      
  
      Babashka runs scripts without a JVM. The first time a project needs a library, it uses your Java install from step 1 to resolve the dependency, then caches it.
      

  
      2. Add a task file
      
  
      Create bb.edn in the project root, next to shadow-cljs.edn:
      

  
      Here's what each part does:
      
  
        
  
      • :deps works like :dependencies in shadow-cljs.edn: it adds babashka/http-server, a small static file server library.
        • 
  
      • :tasks defines named commands you run as bb <name>. :doc is the description bb tasks prints.
        • 
  
      • shell runs a terminal command and stops the task if that command fails. Because release lists test under :depends, a failing test stops the build before it starts.
        • 
  
      • serve requires the server namespace and calls server/exec with the port and the folder to serve.
        • 
  
      

  
      3. Build and serve
      
  
      Make sure the watcher is stopped (see above), then check that Babashka sees your tasks:
      


  
      Build, then serve:
      

  
      The first bb serve takes a few seconds while it downloads the server library; after that it starts instantly. When it prints a line like Serving assets at http://localhost:8000, open http://localhost:8000/index.html. You're now looking at the optimised build. Press Ctrl-c to stop the server.
      
  
      If something goes wrong. bb: command not found means the folder you installed into isn't on your PATH yet; open a new terminal, or check with ls /usr/local/bin/bb or ls ~/.local/bin/bb. An "address already in use" error means another server holds port 8000; change :port in bb.edn. If the page still behaves like the development build, the watcher was running during bb release; stop it and run bb release again.
      
  
      When you're done, stop bb serve and restart npx shadow-cljs watch app test to carry on developing; it replaces the release bundle with a development build again.
      
  
      The one-off compile test, or bb test, is what you'd run in continuous integration: it exits with an error if any test fails. Replicant's development asserts are left out of release builds, so they cost nothing in production.
      

      


      


      

      When something breaks
      

      

      The page is blank
      

      Open the browser console. Check that index.html has <div id="app"> and that the watcher says Build completed with no warnings.
      

      Clicking does nothing
      

      Handlers that are data need set-dispatch!. If you added it to init after the page loaded, refresh once. Look for "Unknown action" in the console: a typo in an action keyword lands there.
      

      Java or version errors when starting shadow-cljs
      

      Recent shadow-cljs releases need a recent JDK. java -version should report 21 or newer.
      

      A warning about the attribute map
      

      Somewhere you wrote [:tag (when ... {...}) ...]. Always pass the map and make its values conditional.
      

      No test output appears in the watcher pane
      

      Start the watcher with both builds: npx shadow-cljs watch app test. Check that shadow-cljs.edn lists "test" in :source-paths and has :autorun true, and restart after changing it.
      

      "Use of undeclared Var" in a test file
      

      The test calls a function from a namespace its ns form doesn't require, or the function isn't written yet (which is expected while a test is red). Compare the ns form with the matching file in step 14.
      

      A test namespace is silently skipped
      

      Its name must end in -test, and its file name uses underscores: reading.ui-test lives in test/reading/ui_test.cljs.
      

      The REPL runs an old version of a test
      

      Require it again with :reload before calling run-tests.
      

      List items behave strangely after removing one
      

      Missing or non-unique :replicant/key. Use the item's id, never its index.
